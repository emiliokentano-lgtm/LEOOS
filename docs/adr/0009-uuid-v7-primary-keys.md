# ADR-0009 — UUID v7 primary keys

**Status:** Accepted · 2026-08-18

## Context

Every table needs a primary key. Three options were realistic:

1. **`bigserial`** — smallest, fastest, perfectly ordered. But sequential
   integers are guessable and enumerable: `/incidents/1042` tells an attacker
   there are at least 1042 incidents, and lets them walk the range. For a system
   holding criminal records that is a real information leak, not a theoretical one.
2. **`uuid` v4** — unguessable, but random. Every insert lands in a different
   part of the B-tree, so the index never stays hot in cache and page splits
   scatter. On a table like `audit_log` or `position_history` this compounds.
3. **`uuid` v7** — unguessable *and* time-ordered. Inserts append to the right of
   the index the way a sequence does, while the random tail keeps ids
   unpredictable.

Postgres 18 gained a native `uuidv7()`. We target Postgres 16, which has not.

## Decision

`uuid` v7, generated by a `uuidv7()` function created in the first migration.

The 12 `rand_a` bits carry sub-millisecond precision (RFC 9562 §6.2 method 3)
rather than randomness, so ids generated inside the same millisecond still sort
in creation order.

## Consequences

**Positive.** Ids are unguessable, so they can appear in URLs without disclosing
volume or ordering. Index locality matches a sequence. `ORDER BY id` is a genuine
creation order, including within a burst — which matters because a dispatch
system writes bursts. Ids can be generated client-side or in another service
without a round trip.

**Negative.** 16 bytes rather than 8, so indexes are roughly twice the size of a
`bigserial` equivalent. Accepted: the tables where this matters most
(`position_history`, `audit_log`) are the ones where index locality matters most
too, and the ordering property buys that back.

The ids leak a creation *timestamp* to anyone holding one. For this system that
is not sensitive — the records themselves carry `created_at` and are visible to
anyone who can see the row.

**Migration path.** When the deployment moves to Postgres 18, the function can be
replaced by the built-in with no schema change: the column type and defaults are
identical. Until then this is ours to maintain, and it carries a conformance test
(version nibble, variant bits, uniqueness, strict ordering across a 500-row burst).

## Note on the implementation

The first attempt built the version nibble with bit-string concatenation
(`b'0111' || value::bit(8)`) and Postgres placed the result in the wrong half of
the byte, producing version-0 UUIDs that looked plausible. Plain integer masking
(`(byte & 15) | 112`) is unambiguous, and the conformance test now asserts the
nibble directly rather than trusting the expression.
